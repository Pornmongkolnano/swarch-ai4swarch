# ADR-0002: ใช้เหตุการณ์เพื่อแยกงานหลังสั่งซื้อ

- **Status:** Proposed
- **Date:** 2026-10-27
- **Deciders:** ยังไม่ระบุ

## Context and problem

ข้อกำหนดที่ผู้ใช้ให้ระบุว่า หลังวางคำสั่งซื้อ Online Boutique ต้องส่งอีเมลยืนยันผ่าน MailFast แทน mock logic ของ emailservice, ให้คะแนนผ่าน loyaltyservice ที่ต้องสร้างใหม่ และบันทึกเหตุการณ์สั่งซื้อให้ฝ่ายการตลาด อีกทั้งคาดว่าจะเพิ่ม SMS, fraud scoring และการปรับปรุง recommendations ในปีถัดไป

ต้องเลือกวิธีประสานงานเหล่านี้โดยรองรับการเพิ่มงานและความล้มเหลวของผู้ให้บริการ ไม่มี context ของระบบเดิม จึงไม่ยืนยัน service ที่รับคำสั่งซื้อ, protocol, ฐานข้อมูล หรือโครงสร้าง deployment ปัจจุบันจากข้อกำหนดนี้

## Decision drivers

ลำดับต่อไปนี้เป็นลำดับที่เสนอเพื่อพิจารณา ยังต้องยืนยันกับผู้ตัดสินใจ

- Modifiability: เพิ่มงานหลังสั่งซื้อได้โดยลดการแก้ไขส่วนรับคำสั่งซื้อ
- Reliability และ availability: งานต้องไม่สูญหาย และความล้มเหลวของงานหนึ่งไม่ขัดขวางงานอื่น
- Correctness: การส่งซ้ำต้องไม่เพิ่มคะแนนหรือบันทึกผลทางธุรกิจซ้ำ
- Operability และ cost: ต้องติดตามและกู้คืนงานได้ โดยประเมินภาระการดูแลเพิ่มเติม

## Considered options

1. ให้ส่วนรับคำสั่งซื้อเรียกทุกงานแบบ synchronous โดยตรง
2. บันทึกรายการงานถาวรให้ตัวประสานงานส่วนกลางเรียกแต่ละบริการแบบ asynchronous
3. เผยแพร่เหตุการณ์ OrderPlaced ผ่าน message broker ให้ผู้รับแต่ละงานทำงานแบบ asynchronous

### Pros and cons of the options

| Option | Pros | Cons |
|---|---|---|
| 1 | เห็นผลตอบกลับของแต่ละงานในเส้นทางเดียว และไม่ต้องเพิ่ม broker | latency และ availability ของคำตอบผูกกับบริการปลายทาง; เพิ่มงานต้องแก้ส่วนรับคำสั่งซื้อ; ความสำเร็จบางส่วนยังต้องจัดการ |
| 2 | แยกงานจากเวลาตอบคำสั่งซื้อ และติดตาม retry ส่วนกลางได้ | ตัวประสานงานต้องรู้จักงานทั้งหมด; การเพิ่มงานต้องแก้ตัวประสานงาน และต้องดูแลคิวงานถาวร |
| 3 | เพิ่มผู้รับเหตุการณ์ได้ และแยกการ retry กับการขยายแต่ละงานได้ | เพิ่ม broker และการติดตามข้ามส่วน; ผลลัพธ์เกิดภายหลัง และต้องจัดการข้อความซ้ำกับการเผยแพร่ที่ล้มเหลว |

## Decision

เสนอเลือกตัวเลือก 3 เพราะรองรับการเพิ่มงานที่ระบุไว้และแยกความล้มเหลวระหว่างงานได้ แนวทางต่อไปนี้เป็นการออกแบบที่เสนอ ไม่ใช่ข้อเท็จจริงจาก source code

- เมื่อคำสั่งซื้อถูกยืนยันอย่างถาวร ให้สร้างเหตุการณ์ OrderPlaced ที่มี event ID, order ID และข้อมูลเท่าที่ผู้รับจำเป็นต้องใช้ โดยกำหนด schema และ version
- ให้ส่วนงานอีเมลแทน mock logic ของ emailservice ด้วยการเรียก MailFast; ให้ loyaltyservice ใหม่รับเหตุการณ์เพื่อให้คะแนน; ให้ผู้รับสำหรับ analytics บันทึกเหตุการณ์ของฝ่ายการตลาด
- ให้แต่ละงานมีสถานะ, retry และช่องทางตรวจสอบ/นำงานที่ล้มเหลวกลับมาทำ พร้อมยืนยันรับข้อความหลังบันทึกผลสำเร็จ
- ใช้การส่งแบบ at-least-once และให้ผู้รับกันผลซ้ำด้วย event ID หรือ order ID ตามความหมายของงาน สำหรับ MailFast ต้องตรวจสอบการรองรับ idempotency และวิธีจัดการกรณีส่งสำเร็จแต่ไม่ได้รับคำตอบก่อนอ้างว่าป้องกันอีเมลซ้ำได้
- ต้องมีวิธีป้องกันช่องว่างระหว่างบันทึกคำสั่งซื้อกับเผยแพร่เหตุการณ์ เช่น transactional outbox หากที่เก็บข้อมูลรองรับ; ยังไม่เลือกกลไกจริงจนทราบขอบเขต transaction
- คำตอบยืนยันวางคำสั่งซื้อไม่รอทุกงานหลังสั่งซื้อเสร็จ ทั้งนี้ต้องยืนยันว่าข้อกำหนดยอมรับการเสร็จภายหลังได้ โดยเฉพาะบทบาทของ fraud scoring ในอนาคต

## Consequences

- **Positive:** เพิ่มงานใหม่ผ่านผู้รับเหตุการณ์และ contract ที่ตกลงกันได้ โดยลดการผูกกับส่วนรับคำสั่งซื้อ (quality attribute: modifiability)
- **Positive:** MailFast หรืองานหนึ่งขัดข้องสามารถค้างรอและ retry โดยงานอื่นยังดำเนินต่อได้ ภายใต้ความสามารถของโครงสร้าง messaging ที่เลือก (quality attribute: availability, reliability)
- **Negative:** ลูกค้าอาจได้รับอีเมลและคะแนนภายหลัง ต้องกำหนดความล่าช้าที่ยอมรับได้ (quality attribute: performance, usability)
- **Negative:** ต้องดูแล broker, schema, สถานะงาน และเครื่องมือติดตามเพิ่มเติม (quality attribute: cost, operability)
- **Risks and mitigations:** คำสั่งซื้ออาจถูกบันทึกแต่เหตุการณ์ไม่ถูกส่ง จึงต้องทดสอบกลไกบันทึกและเผยแพร่ที่กู้คืนได้; ข้อความซ้ำอาจให้คะแนนซ้ำ จึงต้องบันทึกการกันซ้ำร่วมกับผลของงานอย่างสอดคล้องกัน (quality attribute: reliability, correctness)
- **Risks and mitigations:** อีเมลอาจส่งซ้ำเมื่อผลเรียก MailFast ไม่แน่นอน และเหตุการณ์อาจเปิดเผยข้อมูลลูกค้าเกินจำเป็น จึงต้องยืนยันความสามารถของ provider และจำกัดข้อมูล/สิทธิ์เข้าถึง (quality attribute: correctness, security)

## Validation

- ทดสอบวางคำสั่งซื้อแล้วตรวจว่าเกิดอีเมลผ่าน MailFast, คะแนนใน loyaltyservice และ analytics ที่สัมพันธ์กับ order ID เดียวกัน
- ทดสอบผู้รับหยุดทำงาน, MailFast ขัดข้อง, process หยุดระหว่างบันทึกกับเผยแพร่ และข้อความถูกส่งซ้ำ; ตรวจการกู้คืนโดยไม่เสียงานหรือเพิ่มคะแนนซ้ำ พร้อมบันทึกข้อจำกัดการกันอีเมลซ้ำ
- ทดลองเพิ่มผู้รับสำหรับงานอนาคต และตรวจว่าส่วนรับคำสั่งซื้อไม่ต้องแก้เมื่อ contract เดิมเพียงพอ
- วัดเวลาจากยืนยันคำสั่งซื้อถึงแต่ละงานสำเร็จ, จำนวนงานค้าง, retry และงานที่ต้องแก้ไขด้วยคน; กำหนดเกณฑ์ผ่านหลังตกลงเป้าหมายและปริมาณงาน

## Open questions

- ใครเป็นผู้ตัดสินใจ และคุณภาพข้อใดสำคัญที่สุด?
- จุดใดถือว่าวางคำสั่งซื้อสำเร็จ และงานใดต้องสำเร็จก่อนตอบลูกค้า? fraud scoring ในอนาคตมีหน้าที่ขัดขวางคำสั่งซื้อหรือไม่?
- ปริมาณงาน, เป้าหมาย latency, ระยะเวลาที่งานต้องเสร็จ, งบประมาณ และทักษะทีมเป็นอย่างไร?
- ระบบใช้ที่เก็บข้อมูลและ transaction แบบใด และจะใช้กลไกใดเชื่อมการบันทึกคำสั่งซื้อกับเหตุการณ์?
- จะเลือก broker, การเก็บรักษาเหตุการณ์, retry, การ replay และผู้รับผิดชอบงานล้มเหลวอย่างไร?
- MailFast มี API, rate limit และ idempotency หรือการตรวจสอบผลการส่งอย่างไร?
- คะแนนคำนวณอย่างไร และการยกเลิก/คืนเงินต้องปรับคะแนนหรือเหตุการณ์อย่างไร?
- ปลายทาง analytics, event schema, สิทธิ์เข้าถึงและข้อจำกัดข้อมูลลูกค้าคืออะไร?
